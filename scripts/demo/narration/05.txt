A review does not have to be one reader. The Review panel workflow has the Coder write the change, and then a fork node splits the run into three branches: a security reviewer, a performance reviewer and a maintainability reviewer, each looking at the same code for its own concern. A join node waits for all three, and a lead Reviewer merges their verdicts into one. If the lead asks for changes the work goes back to the Coder; if it approves, the run stops at the human gate and then the Deployer opens the merge request. Here is a run of it. The Coder finishes, and the three reviewers start at the same moment: the header counts three branches running, and the fork card shows one column per branch, each with its own model calls and tool calls. When the last one finishes, the join card closes the fork, the lead reads the three verdicts and gives one of its own, and the run waits at the gate. I approve it, and approve the merge request when the Deployer asks. The run succeeds, and the merge request is linked from the summary, carrying the work three reviewers have already read.
